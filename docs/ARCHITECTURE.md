# Архитектура FinanceOS

## Общая схема

```text
Telegram user
     ↕ команды, текст, callback query, изображения
Telegram Bot API
     ↕ long polling (python-telegram-bot)
app/main.py → app/handlers.py → app/sheets.py → gspread → Google Sheets API
                         ├──→ app/reports.py
                         └──→ app/charts.py → tmp/charts/*.png
```

Приложение — монолитный асинхронный Telegram-бот. Telegram-сценарии работают асинхронно, а репозиторий Google Sheets предоставляет синхронный слой хранения. Сервер приложения не хранит финансовые данные локально.

## Назначение основных модулей

- `app/main.py` — точка входа: загружает настройки, создаёт `Application`, регистрирует команды, callback- и message-handlers, запускает long polling.
- `app/handlers.py` — Telegram UI и orchestration: меню, пошаговый ввод, проверка пользовательских данных, вызов репозитория, отчётов и диаграмм. Черновики сценариев находятся в `context.user_data`.
- `app/sheets.py` — `SheetsRepository`: создание и проверка листов, CRUD операций, планов, долгов, целей и категорий.
- `app/reports.py` — чистые расчёты план/факт, месячных показателей, прогнозов, финансового здоровья и форматирование отчётов.
- `app/config.py` — загрузка `.env`, проверка обязательных переменных и выбор JSON либо файла service account.
- `app/charts.py` — построение PNG через matplotlib в headless-режиме; временный файл удаляется handler после отправки.
- `app/chat_history.py` — только оперативный in-memory список последних Telegram message ID для команды очистки чата.

## Хранение данных

Google Sheets является источником истины. Данные разделены по `telegram_user_id`:

| Лист | Содержимое |
|---|---|
| `Transactions` (настраивается) | доходы и расходы |
| `StartupState` | последний снимок стартового состояния пользователя |
| `BudgetPlan` | месячные планы по категориям |
| `Debts` | состояние долгов |
| `DebtPayments` | журнал платежей по долгам |
| `Goals` | финансовые цели и прогресс |
| `Categories` | справочник категорий |

Строки содержат UTC ISO timestamp. Репозиторий создаёт отсутствующие листы и заголовки; неожиданная схема служебного листа вызывает ошибку, чтобы не повредить данные. `StartupState` заменяется для пользователя, планы обновляются по ключу пользователь + месяц + категория. Долги и цели закрываются сменой статуса, а не физическим удалением.

## Callback-кнопки

Inline-кнопка содержит компактный `callback_data` с пространством имён: `menu:`, `action:`, `delete_operation:` или `category:`. Один `CallbackQueryHandler` в `main.py` фильтрует эти значения и передаёт запрос в `menu_callback`. Handler подтверждает callback, разбирает префикс и запускает тот же сценарий, что доступен прямой командой. Состояние многошагового ввода хранится по ключам в `context.user_data`; `/cancel` очищает его.

## Бизнес-логика

Handlers получают строки пользователя из репозитория и передают их в функции `reports.py`. Расчёты используют `Decimal`, UTC-границы месяца и, при наличии, последний `StartupState`. Отчёт не сохраняется: он каждый раз строится из актуальных строк. Диаграммы используют те же наборы данных и расчёт бюджета. Изменение или удаление строки операции поэтому сразу отражается в следующем отчёте; отдельного кэша агрегатов нет. Формулы и ограничения описаны в [BUSINESS_LOGIC.md](BUSINESS_LOGIC.md).
